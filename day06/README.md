# Day 06｜MFA 已通過，為什麼還是 AccessDenied？

## 情境

Authentication（身分驗證）用來確認「提出請求的是誰」，Authorization（授權）則決定「這個身分可以做哪些操作」。

即使密碼與 MFA 都驗證成功，也只是代表身分驗證通過。之後使用 AWS Console 或 CLI 執行操作時，仍然需要經過 AWS 的授權判斷。

一位新人使用自己的 IAM User 登入 AWS：

* 密碼與 MFA 都成功。
* 可以列出 IAM 使用者。
* 查看 EC2 時出現 `AccessDenied`。

管理員確認，這位新人目前的政策只允許課堂使用的 IAM 查詢，**沒有授予 EC2 查詢權限**。

---

## 第 1 題－登入成功能確認什麼？

根據流程圖，新人已通過密碼與 MFA 驗證。從這兩項驗證成功的結果，可以直接確認以下哪一項說法？

A. 新人至少已經有權限查詢各個 AWS 服務的資料。
B. 新人已完成這次登入的身分驗證。
C. 通過 MFA 後，新人就會取得原本缺少的 EC2 查詢權限。
D. 新人之後改用 CLI 操作時，不需要再提供憑證。

### 答案

**B**

### 理由

密碼與 MFA 都成功，代表新人已完成這次登入的**身分驗證（Authentication）**。

但是否能查詢 EC2，屬於**授權（Authorization）**，仍要看目前 IAM 政策是否有授予對應權限。

### 這題要記住

**Authentication：確認你是誰。**
**Authorization：確認你可以做什麼。**

通過 MFA 不等於取得更多 AWS 資源的操作權限。

---

## 第 2 題－如何回覆新人的疑問？

根據管理員確認的權限設定，以下哪一則回覆能解釋新人遇到的狀況，也能避免他進行不必要的操作？

A. 再做一次 MFA，AWS 就會信任剛才被拒絕的 EC2 操作，允許這次查詢。
B. Console 沒有權限時，可以改用 CLI，因為 CLI 的操作由另一套權限規則決定。
C. 登入成功表示身分驗證已通過；EC2 查詢被拒絕，是因為目前沒有這項授權，換成 CLI 或重做 MFA 都不會補上權限。
D. IAM 查詢已經成功，EC2 查詢被拒絕可能只是新政策還沒生效，先等幾分鐘再試一次即可。

### 答案

**C**

### 理由

新人已經完成身分驗證，但目前 IAM 政策沒有授予 EC2 查詢權限，因此 EC2 操作會被 `AccessDenied`。

換成 CLI 或重新進行 MFA，都不會自動增加原本缺少的授權。

---

## 第 3 題－新增 EC2 查詢需求後如何處理？

老師要求這位新人查看 EC2 清單，管理員確認：**要完成這項任務，新人目前就只差 EC2 的查看權限**。

依照最小權限原則，只給完成任務所需的權限。以下哪兩項處理方式，能符合這個原則，並確認新人可以完成任務？

A. 授予新人整個帳號的完整管理權限，避免日後還需要調整。
B. 關閉 MFA，讓新人的請求跳過權限判斷。
C. 依照任務所需的 EC2 查詢操作，補上最小必要範圍的 Allow。
D. 由管理員使用自己的身分確認能開啟 EC2 清單，就視為新人已能完成任務。
E. 權限調整生效後，使用這位新人原本的 IAM User，確認任務所需的 EC2 查詢是否成功。

### 答案

**C、E**

### 理由

新人只需要查看 EC2，因此應依照實際任務補上**最小必要範圍的 Allow**，而不是直接給予完整管理權限。

權限調整後，還要使用新人的 IAM User 實際執行 EC2 查詢，才能確認權限確實套用到正確的身分，並且足以完成任務。

設定權限時，也要依照各項操作支援的資源範圍來限制權限，避免授予不必要的存取範圍。

### 這題要記住

**最小權限原則（Least Privilege）**：

只給完成目前任務所需要的權限。

另外，**管理員自己能做得到，不代表新人也有相同權限**，權限是否生效要用實際執行任務的身分確認。
