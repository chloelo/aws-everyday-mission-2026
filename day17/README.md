# Day 17｜回應與新連線，SG 如何區分？

## 題目情境

Security Group（SG）具有 stateful（有狀態）特性，會追蹤已允許的連線。只要連線仍在追蹤，對方沿著該連線送回的正常回應不需要另外設定反方向規則。

如果對方主動發起另一條新連線，則仍須符合接收端 SG 的 Inbound 規則。

Web 主機只掛載名稱為 `web-sg` 的 SG，完整規則如下：

| 方向 | 規則 |
| --- | --- |
| Inbound（連入 Web） | 沒有規則 |
| Outbound（Web 連出） | 允許 Web 連往 API `198.51.100.20/32` 的 TCP 443 |

Web 和 API 之間有三個事件：

- **事件①｜Web 發起連線：** Web 從本機臨時 port `49152` 連向 API 的 TCP 443。`49152` 用來接收同一條連線的回應。
- **事件②｜API 回應：** API 沿著事件①那條仍在追蹤的連線，回傳結果到 Web 的 `49152`。
- **事件③｜API 發起新連線：** API 在回應完後，另外開一條新連線，連向 Web 的 TCP `49152`。

本題只判斷 SG；路由、NACL、作業系統與服務皆正常。

## 第 1 題－同一個 port，不同連線（單選）

事件②與③都送到 Web 的 `49152`。為什麼不能只看目的 port，就把兩者視為同一條連線？

A. 因為 SG 是靠時間分辨：事件②緊接在事件①之後回來，事件③是等回應結束後才另外連進來。  
B. 事件②屬於事件①已允許且仍在追蹤中的同一條連線；事件③則是 API 另外發起的一條新連線。  
C. 事件②是 Web 向 API 的 TCP 443 發起連線後收到的回應，SG 會再次用這條 Outbound 規則放行；只有事件③需要比對 Web 的 Inbound 規則。  
D. 因為 SG 只比對來源 IP 與目的 port，這兩項在事件②與③都相同，其實應該視為同一回事。

### 答案

B

### 理由

事件②是事件①已允許連線的回應，仍屬於同一條受追蹤的連線。事件③則是 API 另行發起的新連線。目的 port 相同，不代表連線關係相同。

## 第 2 題－Web 的 SG 會放行哪些事件（複選，請選 2 項）

根據上述事件與 `web-sg` 的完整規則，以下哪兩項判斷正確？

A. 事件②會通過 SG，因為它是事件①已允許連線的正常回應。  
B. 事件②會被 SG 擋住，因為 Inbound 沒有明列 TCP 49152。  
C. 事件③會被 SG 擋住，因為它是另一條新連線，沒有適用的 Inbound Allow。  
D. 事件③會通過 SG，因為 API 的 IP 已出現在 Outbound 規則裡。  
E. 事件③會通過 SG，因為相同來源曾經成功使用 Web 的 49152。

### 答案

A、C

### 理由

事件②是 Web 已允許連線的正常回應，因此會依 SG 的連線追蹤通過，不需要另外增加 Inbound 規則。事件③是 API 主動建立的新連線；`web-sg` 沒有 Inbound 規則可允許它進入 Web。

## 第 3 題－改連 API 的 TCP 8443（單選）

這一題改用另一種情況：Web 首次向同一個 API 的 TCP 8443 發起全新連線。`web-sg` 的 Outbound 仍只允許 TCP 443，沒有既存相關連線或其他 SG 規則。這邊只判斷 SG，結果為何？

A. 允許，因為出站預設全開，443 那條只是多加的。  
B. 允許，因為 Web 先前連過這個 API，追蹤狀態可以沿用到 8443。  
C. 拒絕，因為 8443 不符合唯一那條 Outbound 規則。  
D. 允許，因為規則已允許到這個目的 IP，port 只影響對方哪個服務接聽。

### 答案

C

### 理由

這是目的 port 為 TCP 8443 的新連線，但題目給定的唯一 Outbound 規則只允許 TCP 443。目的 IP 相同仍不足以通過；目的 port 也必須符合規則。

### 這題要記住

SG 會追蹤已允許連線的狀態，因此正常回應不必另開反方向規則；但另一方主動發起的新連線，仍須符合接收端的 Inbound 規則。SG 規則也會檢查協定與 port，先前對同一個 IP 的允許不會自動涵蓋其他 port。
